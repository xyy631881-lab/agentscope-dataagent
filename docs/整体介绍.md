# agentscope-dataagent 整体介绍

> 版本：2.0.0-SNAPSHOT
>
> 更新时间：2026-07-13
> 当前定位：多租户、自进化的企业数据分析 Agent 平台

## 1. 产品定位

dataagent 面向企业数据分析团队：每位分析师拥有一个私有 data agent，agent 会随个人习惯、常用 SQL、图表偏好和业务知识持续进化；团队可以把优秀的 SQL 技能、子智能体、图表模板和分析方法通过审批流程沉淀到共享库，其他成员按版本安装和复用。

核心原则：

- 私有进化：用户的 workspace、记忆、会话和运行产物彼此隔离。
- 团队沉淀：共享能力必须经过审批、版本化发布、可回滚。
- 框架托管运行时：AgentScope 负责 AgentState、Workspace、Filesystem、Sandbox 生命周期；应用层只负责产品策略、权限、审计和资产治理。
- 企业可治理：所有业务元数据、审批流、分享授权、会话索引和审计事件进入 MySQL。

## 2. 技术栈

| 层 | 当前实现 |
|---|---|
| 后端 | Spring Boot 3 + Spring MVC + Spring Security |
| Agent 引擎 | AgentScope Java 2.0 HarnessAgent |
| 模型 | LongCat/OpenAI-compatible API 或本地 Ollama |
| 业务库 | MySQL，当前持久层适配为 Spring Data JPA |
| Runtime 状态 | Redis AgentStateStore + Redis sandbox snapshot + Redis execution guard |
| 沙箱 | AgentScope DockerFilesystemSpec，`IsolationScope.USER` |
| 前端 | React + TypeScript + Vite + SSE |
| 图表 | Vega-Lite/Vega Embed，前端安全渲染内联 `data.values` |

### MySQL 可以不用 JPA 吗？

可以。企业项目完全可以选 MyBatis、jOOQ 或 JdbcTemplate。

但当前代码已经有大量 `Entity + Repository + @Transactional` 实现，直接把 JPA 全量替换成 MyBatis 会影响登录、用户、Agent、会话、审批、市场等多个域。推荐策略是：

1. 保持业务库为 MySQL。
2. 当前版本继续使用 JPA 作为基础设施适配层。
3. 新业务先通过 application/domain 接口暴露能力，不让 Controller 直接依赖 JPA。
4. 后续若迁移 MyBatis，只替换 `infrastructure` 层，不动 API、domain、application 语义。

也就是说：不是不能不用 JPA，而是不建议在沙箱/工作区重构这一轮同时做持久层大迁移。

## 3. 数据边界

| 数据 | Source of truth | 说明 |
|---|---|---|
| 用户、租户、Agent 定义、分享、审批、市场版本、会话索引 | MySQL | 应用业务事实，适合查询、分页、审计和权限校验 |
| 请求级 Token/缓存 Token/成本/耗时、运行记录与 OTel span 索引 | MySQL | 用量和可观测性事实，按用户、Agent、模型、会话和 trace 查询 |
| 租户模型连接、加密 API Key、Base URL、模型单价 | MySQL | 当前以用户 ID 作为过渡 tenant ID；API Key 仅可写入、不可回显 |
| 对话上下文、Plan 状态、工具上下文、权限上下文 | AgentStateStore | AgentScope runtime 状态，生产启用 Redis |
| `AGENTS.md`、`skills/`、`subagents/`、`knowledge/`、`plans/`、`artifacts/` | Workspace | agent 定义与运行产物的事实来源 |
| Docker 容器、临时 shell/python 执行环境 | Sandbox | 可回收，不作为业务事实来源 |
| `local-workspaces/{userId}/{agentId}` | 本地只读镜像 | 方便本机查看 sandbox `/workspace` 内容，不作为写入源 |

## 4. Runtime 与沙箱设计

最终方案：采用 AgentScope 框架生命周期，不再自建 `UserSandboxPool`、`SandboxLock`、`SandboxReaperService` 或心跳控制器。

当前执行链路：

```text
聊天工具调用 / 工作区文件操作
  -> AgentScope WorkspaceManager / SharedSandboxFilesystem
  -> SandboxManager.acquire(context, RuntimeContext(userId))
  -> sandbox.start()
  -> execute / upload / download / ls / read
  -> SandboxManager.persistState(...)
  -> SandboxManager.release(...) + lease.close()
```

应用层只配置这些策略：

- `SandboxClient`：当前是 Docker，带 Windows Docker Desktop 兼容适配。
- `SandboxSnapshotSpec`：redis profile 下使用 Redis snapshot；未启用时为 Noop。
- `SandboxExecutionGuard`：redis profile 下用 Redis guard 串行化同一隔离槽执行。
- `AgentStateStore`：redis profile 下用 RedisAgentStateStore。

配置口径已统一为：

```yaml
dataagent:
  runtime:
    redis:
      enabled: true
      key-prefix: dataagent:runtime:
```

旧口径 `dataagent.session.redis` 不再用于 runtime。会话元数据在 MySQL，不在 Redis。

## 5. Workspace 目录语义

运行时容器内固定视角：

```text
/workspace
  AGENTS.md
  MEMORY.md
  skills/
  subagents/
  knowledge/
  plans/
  artifacts/
    charts/
    reports/
    datasets/
  agents/{runtimeAgentId}/sessions/
```

前端工作区页面会同时展示：

- 运行时工作区：`/workspace`
- Agent 定义目录：宿主机上的 agent workspace 路径
- 本地镜像：`local-workspaces/{userId}/{agentId}`

注意：本地镜像只读，用于用户查看；真实写入仍通过 Workspace API 和框架 sandbox 文件系统完成。

## 6. 共享能力与自进化

个人 agent 的新能力先进入个人草稿或贡献记录：

```text
users/{userId}/agents/{agentId}/skills/_drafts/
users/{userId}/agents/{agentId}/subagents/
users/{userId}/agents/{agentId}/artifacts/
```

通过审批后，发布到共享库：

```text
marketplace/tenants/{tenantId}/
  skills/{name}/{version}/
  subagents/{name}/{version}/
  chart-templates/{name}/{version}/
  sql-recipes/{name}/{version}/
```

发布要求：

- 版本不可变，只能新增版本。
- 记录提交人、审批人、来源 workspace、测试样例和风险说明。
- SQL 技能必须只读，禁止 DDL/DML。
- 图表模板必须使用内联或受控数据源，禁止任意远程 URL。

## 8. 本地启动

默认 profile 使用 MySQL + Redis：

```bash
mvn compile
mvn package -DskipTests
java -jar target/agentscope-dataagent-2.0.0-SNAPSHOT-exec.jar
```

前端独立调试：

```bash
cd frontend
npm install
npm run dev
```

生产打包前端进后端静态目录：

```bash
mvn -Pfrontend package -DskipTests
```

### 模型凭据与成本配置

不要再把 API Key 写进 `application.yml`。静态 LongCat 使用环境变量：

```powershell
$env:LONGCAT_API_KEY = "..."
$env:DATAAGENT_CREDENTIAL_ENCRYPTION_KEY = "a-long-random-stable-secret"
```

`DATAAGENT_CREDENTIAL_ENCRYPTION_KEY` 用于 AES-GCM 加密租户模型 API Key，生产必须是独立且稳定的值；改变它会导致旧密钥无法解密。用户可在前端“模型连接”页配置 `longcat` 或其他逻辑模型的提供商、Base URL、模型名、密钥和单价。该页不回显密钥。

当前采用渐进策略：个人自定义 Agent 创建或因配置失效重建时使用该租户连接；没有配置的个人 Agent，以及现有全局 Data Agent，继续使用 `local/longcat` 静态注册模型。LongCat 保持 AgentScope 的结构化输出 fallback，未启用 native JSON Schema。

### 用量与运行记录

每次聊天请求会聚合本次内所有 `ModelCallEndEvent` 的 `ChatUsage`：

- `inputTokens`、`outputTokens`、`cachedPromptTokens`
- 请求总耗时、实际执行模型、配置单价计算出的 `costMicrousd`
- `SUCCESS`、`CANCELLED`、`ERROR` 状态

运行记录由 `OtelTracingMiddleware` 生成 Agent、模型和工具 span；应用只持久化用于排障的白名单属性（模型、token、工具名、调用数、reply id），不会将提示词或模型正文写入 span 索引。

## 9. 今日重构结论

本项目的 runtime 方向已经收敛为：

```text
MySQL 管业务事实
Redis 管 AgentScope runtime 状态
Workspace 管 agent 定义和产物
Sandbox 管一次执行环境
Local mirror 管本地可查看副本
Otel span index 管可查询的运行记录
```

不要再引入应用自管容器池。需要扩展时优先接 AgentScope 提供的 Workspace、Filesystem、Sandbox 生命周期点。
