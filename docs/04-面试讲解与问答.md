# 面试讲解与问答

本章的目标是让面试表达与代码证据一致。回答时优先使用“目标 - 设计 - 取舍 - 验证 - 边界”的结构，不要把计划中的能力说成线上 SLA。

## 1. 一分钟项目介绍

我做的是一个基于 AgentScope Java 2.0 的多用户数据智能体平台。用户能创建私有 Agent，通过流式聊天调用数据发现、表结构、只读 SQL 和图表工具，在隔离工作区里沉淀报告、技能和子 Agent。平台层不是只做聊天，而是把用户、Agent ACL、会话、Docker Sandbox、模型密钥、能力市场审批、Token 成本和 OpenTelemetry 运行记录整合起来。技术上后端是 Spring Boot + MySQL，运行状态和 Sandbox snapshot 可用 Redis 承载，前端是 React + TypeScript + SSE。近期我重点解决了同名私有 Agent 的工作区隔离、卸载 Skill 不应自动复活、统一个人/平台用量页以及固定视口导致的长页面无法滚动等问题。

## 2. 三分钟项目介绍

项目面向需要反复做 SQL、图表和报告的分析人员。第一层是交互：React 前端通过 SSE 显示模型 token、工具轨迹和人工确认，敏感 SQL 在确认后才执行。第二层是 Agent 运行时：AgentScope `HarnessAgent` 负责模型、工具、子 Agent、Workspace 和 Sandbox 生命周期，应用层统一注入 Plan、Memory、权限和数据工具。第三层是治理：MySQL 保存用户、Agent、会话、审批、用量和 Trace；Redis 在启用后保存运行态、快照和执行 guard；Workspace 保存提示词、Skill、子 Agent 和产物。

多租户的核心不是给每个 Agent 起不同名字，而是所有路径和状态键都以用户边界隔离。我们发现两个用户同名 `personal-agent` 会共享默认定义目录，于是新增 `userWorkspacePath(userId, agentId)`，并把 Agent 创建、页面读取和聊天运行时全部统一到 `.agentscope/users/{userId}/agents/{agentId}`。同时，历史 Agent 的基础 Skill 迁移用 marker 控制，避免用户卸载 Skill 后后台“自动补齐”又把它写回来。

可观测性方面，一次聊天会汇总本回合所有模型调用，写入 Token、缓存 Token、耗时、成本和状态；OTel span 只保存白名单属性，避免 Prompt 和密钥进入审计表。前端把个人和平台用量收敛到同一个页面，普通用户只能看个人数据，管理员可看平台汇总和排行。当前项目已经有 84 个通过的单元测试，但我会明确说明多实例压测、Skill 供应链扫描和跨资源一致性仍是后续工作。

## 3. 高频问答

### Q1：为什么选 AgentScope，而不是自己写 Agent 循环？

**答**：模型调用、工具协议、会话状态、Sandbox、Workspace 和子 Agent 都是跨请求的复杂生命周期。自己实现容易出现状态泄漏、资源回收和事件顺序不一致。项目把这些运行时能力交给 AgentScope，应用层只负责用户身份、权限、数据工具、审批和审计。这样框架升级或替换基础设施时，业务边界更清楚。

### Q2：多 Agent 与一个 Agent 调多个工具有什么区别？

**答**：工具是确定性能力，例如执行只读 SQL；子 Agent 是带独立提示词、模型、迭代限制、上下文和工作区策略的任务执行单元。主 Agent 可将“查数据”和“写报告”分给不同子 Agent，再综合结果。子 Agent 带来专业分工，但也会增加 Token、延迟、上下文传递和可观测性复杂度，因此不应该为每个小步骤都委派。

### Q3：如何保证不同用户不串工作区？

**答**：定义工作区的物理路径由 `userId + agentId` 组成，不再信任仅按 Agent 名称的默认路径；控制面和运行时均调用同一个 `userWorkspacePath`。Sandbox 状态命名空间也使用用户边界。测试中验证不同用户同名 `personal-agent` 得到不同路径。仅靠前端 URL 隔离没有安全意义，关键在服务端路径和授权检查。

### Q4：为什么删除 Skill 后会“复活”？你怎么修？

**答**：旧逻辑在每次列举私有 Agent 时都尝试补齐团队基础 Skill，它无法区分“首次初始化缺失”和“用户主动卸载”。修复是引入一次性迁移 marker；历史 Agent 若已有任何 Skill 目录，说明已经初始化，只写 marker，不复制缺失 Skill。前端还禁用了技能列表缓存，并在删除成功后先更新本地状态、再向服务端确认。

### Q5：SSE 的关键难点是什么？

**答**：不是把字符串不断 flush 就结束了。需要维护事件顺序、工具调用 ID、人工确认上下文、客户端取消、异常终止和最终资源清理。尤其不能在首个 SSE 事件前做可能慢的非关键审计或 Sandbox 恢复，否则用户会感到“没有响应”。项目把用量、Trace、会话和工作区演化作为回合结束后的归档，并让观测失败不阻断主回复。

### Q6：SQL 工具如何防止危险操作？

**答**：采用多层限制：工具级只读语义、语句校验、行数限制、查询超时、人工确认，生产上还应该使用数据库只读账号。关键词过滤只能减少明显风险，不能证明 SQL 安全；CTE、注释、多语句和数据库方言都可能绕过简单正则。因此我会把 AST 解析和只读数据库账号作为后续增强，而不是声称当前实现绝对安全。

### Q7：为什么 MySQL、Redis、文件系统都要用？

**答**：它们保存的对象不同。MySQL 是业务事实和审计查询的权威；Redis 适合 AgentState、Sandbox snapshot 与短期执行协调；Workspace 是 Agent 的文件化定义和产物；Docker 只是执行环境。把所有东西塞进一个库会牺牲框架运行时语义，把业务事实塞进 Redis 又会影响审计、分页和恢复。

### Q8：Redis execution guard 解决什么问题？

**答**：同一用户隔离槽如果并发恢复/写入 Sandbox，可能出现文件竞争、状态覆盖或同一容器被同时操作。guard 用分布式协调将同一槽串行化。它的边界是 lease 过期和客户端故障，因此生产上必须有租约续期、幂等写入、超时与观测，而不能只依赖一个锁。

### Q9：Windows Docker 为什么容易出问题？

**答**：宿主机 Java `Path` 与 Linux 容器路径语义不同。`/workspace` 在 Windows 上可能被转换为反斜杠，再被容器 shell 当作转义，最终创建错误目录。项目在 Docker Sandbox 启动前后直接用 POSIX 字符串创建 `/workspace`，并加有限重试和容器状态探测。核心原则是跨边界时不要拿宿主机路径 API 表示容器路径。

### Q10：用量是如何统计的？

**答**：以“一个完成的聊天请求”为账本粒度，聚合该回合内所有 `ModelCallEndEvent` 的 input、output、cached Prompt Token、模型、耗时和成本，最终写一条 `UsageEvent`。页面再按用户、平台、模型、小时、天聚合。这个口径能避免只统计最终模型调用而漏掉子 Agent 或重试，但要注意重试是否应该计费取决于实际供应商账单口径。

### Q11：如何避免 Trace 泄露 Prompt 或 API Key？

**答**：TraceRunService 使用属性白名单，只保存模型名、Token、工具名、调用数、reply id 和错误类型；不把消息正文、工具参数、模型响应或 API Key 放入 span 索引。日志和异常摘要也需要截断和脱敏。可观测不是“把一切都记录下来”。

### Q12：模型密钥如何保护？

**答**：用户模型配置通过 API 写入，密钥用 AES-GCM 加密存储，读取接口只显示是否已配置而不回显密钥。Agent 构建时解密并生成模型上下文；未配置或解析失败时回退静态模型。生产中还应轮换主密钥、限制数据库访问和接入专用密钥管理服务。

### Q13：审批发布为什么难做？

**答**：审批记录在 MySQL，Skill 版本是文件目录，安装后还要失效 Redis/Sandbox 状态，这三个资源没有天然事务。当前做 staging、版本归档和可重试，保证失败可见；更进一步应做 Outbox、补偿任务和 manifest 对账。不能简单用一个 `@Transactional` 假装文件系统与 Redis 已经原子提交。

### Q14：为什么个人与平台用量要放在同一页？

**答**：它们的指标结构和图表几乎一致，两套页面会产生 UI 与口径漂移。共享展示组件按 scope 选择接口：普通用户只有个人 scope，管理员可切平台 scope。后台菜单只保留治理特有功能，减少重复入口；但后端仍严格限制平台接口。

### Q15：项目遇到的最大返工是什么？

**答**：最典型的是把“Agent 运行时”和“产品层”混在一起的风险，例如自建容器池、只修页面路径却漏修聊天运行时、用“自动补齐”替代显式迁移。后来收敛为：框架管理 Sandbox/State 生命周期，应用统一管理用户边界、策略和审计；所有控制面和运行时路径通过一个工厂方法解析。这比补丁式修复更重要。
