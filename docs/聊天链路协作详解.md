## 一、先看懂业务：这是个什么系统

本项目是一个**多租户数据分析 Agent 平台**。说白了就是一个"AI 数据分析师的客服中心"：

- 多个用户（租户）可以登录
- 每个用户能选择不同的 Agent（数据分析师）聊天
- 每个用户跟每个 Agent 可以有多个独立会话（像 ChatGPT 左侧栏那样）
- 用户发消息后，Agent 会调用工具（查数据库、画图、生成报表）来回答

**关键约束**：用户 A 绝不能看到用户 B 的会话，用户 A 跟 Agent1 的会话也不能串到 Agent2。这就是"多租户隔离"。

## 二、四个角色的分工（餐厅比喻）

把整个系统想象成一家**连锁餐厅**，每个文件扮演一个角色：

| 文件 | 餐厅角色 | 实际职责 |
|---|---|---|
| **ChatController** | 服务员 | 接待顾客点单（收消息）、上菜（返回回复） |
| **SessionController** | 前台经理 | 管理包间（会话列表、查历史、删包间） |
| **SessionAgentManager** | 餐厅大堂调度 | 记住所有包间在哪个位置（会话注册表，但不创建包间） |
| **SessionStore** | 仓库管理员 | 把包间登记册锁进保险柜（持久化到磁盘） |

### 它们之间的关系

```
顾客（用户浏览器）
    │
    │ HTTP 请求
    ▼
┌─────────────────────────────────────────────┐
│  服务员 ChatController                        │
│  ├─ 接点单（chat/stream）                      │
│  └─ 转给后厨（Agent）                          │
└─────────────────────────────────────────────┘
    │                              │
    │ 查会话是否存在                │ 不查会话、不创建会话
    ▼                              │
┌─────────────────────────────────────────────┐
│  大堂调度 SessionAgentManager（内存）          │
│  ├─ 记住每个包间的位置（从 sessions.json 加载）│
│  ├─ 查包间存不存在                             │
│  ├─ 重置/删除包间                              │
│  └─ ⚠️ 不创建新包间（创建是 harness 干的）     │
└─────────────────────────────────────────────┘
    │                              ▲
    │ 同步                         │ 恢复
    ▼                              │
┌─────────────────────────────────────────────┐
│  仓库 SessionStore（磁盘 sessions.json）      │
│  ├─ harness 框架运行时写入新会话               │
│  └─ 启动时把包间册子还给大堂                   │
└─────────────────────────────────────────────┘

    另一条线：
┌─────────────────────────────────────────────┐
│  前台经理 SessionController                   │
│  ├─ 列出包间（inbox）                         │
│  ├─ 查包间历史（turns）                       │
│  ├─ 清空包间（reset）                         │
│  └─ 注销包间（delete）                        │
└─────────────────────────────────────────────┘
    │
    │ 也调 SessionAgentManager
    ▼
```

**核心要点**：
- `ChatController` 和 `SessionController` 是**两个并列的入口**，都依赖 `SessionAgentManager`
- `SessionAgentManager` 是**查询/管理中枢**，但它**不创建会话**——创建是 harness 框架的活
- `SessionStore` 是 `SessionAgentManager` 的**小弟**，只管读写磁盘
- **harness 框架直接写 `sessions.json`**，SessionAgentManager 只在启动时读一次

## 三、场景一：用户发一条消息（最核心的链路）

这是最重要的一条链路。假设用户 `alice` 在 `数据分析师` 这个 Agent 上发了一条消息："帮我查一下上个月销量"。

### ⚠️ 重要澄清：stream 接口不查会话、不创建会话

先纠正一个常见误解。很多人以为 `POST /chat/stream` 这个接口会查会话、创建会话——**它不会**。

- `stream()` 接口**只干一件事**：打包消息丢给通道，然后把 Agent 的事件流翻译成 SSE
- **查会话**是另一个接口 `GET /chat/session`（`currentSession()`）干的
- **创建会话**是 harness 框架内部（ChatUiChannel + 网关）干的，**本项目代码看不到**

`ChatController` 调用 `SessionAgentManager` 的地方只有两处：
1. `findSessionKeyByGate()` ← 给 `currentSession` 接口用，查会话存不存在
2. `resetSession()` ← 给 `/reset` 斜杠命令用

**发送消息这条主链路根本不直接调 SessionAgentManager**。会话的创建/注册是 harness 框架在 `dispatchStream` 内部自动完成的。

### 关键步骤详解

#### 步骤 1-5：接待与拦截（ChatController 的全部工作）
用户消息进来，ChatController 先做四件事：
1. **验明身份**：从 JWT 拿到 `userId = "alice"`
2. **权限检查**：确认 alice 有权跟这个 Agent 聊天
3. **确定会话**：用户传了 `sessionKey="s1"` 就用它，没传就生成 UUID
4. **斜杠命令短路**：如果是 `/new`、`/reset` 等命令，直接返回不经过 Agent

**注意**：这一步**不查会话存不存在**。即使会话不存在，消息也会照常发出去——harness 框架会在内部自动创建会话。

#### 步骤 6-7：打包与派发（ChatController → 通道）
ChatController 把用户消息打包成 `InboundMessage`，贴上三个关键标签：
- `userId` = alice（谁发的）
- `preferredAgentId` = agent1（给哪个 Agent，通过 catalog 查出来）
- `accountId` = s1（conversationId，哪个会话）

然后丢给 `chatUiChannel.dispatchStream(inbound)`。**从这一步开始，ChatController 就退出舞台了**，它只等着收事件流。

#### 步骤 8-9：框架内部干的事（本项目代码不可见）
`dispatchStream` 进去之后，harness 框架（ChatUiChannel + HarnessGateway）会：
1. **算 gateKey**：根据 InboundMessage 的三个标签算出 `|x:agentId=agent1|t:s1`
2. **查/建会话**：框架内部维护着自己的会话注册表，gateKey 没对应会话就自动建一个

**这部分代码不在本项目里**——`ChatUiChannel`、`HarnessGateway` 都是 `agentscope-harness` 框架的类，本项目只是调用 `dispatchStream` 这个入口。框架内部怎么管会话，本项目不关心也看不见。

#### 步骤 10-11：Agent 干活
框架把消息投给 Agent，Agent 调用工具（run_sql、draw_chart）生成回复。

#### 步骤 12-14：流式返回
Agent 每生成一个事件（吐一个字、调一次工具），框架就推给 ChatController。ChatController 把这些事件翻译成前端能懂的 SSE 格式，浏览器实时显示。

## 三·补：那 currentSession 接口是干啥的？

`currentSession()` 接口（`GET /api/agents/{agentId}/chat/session`）是**前端用来探路的**——在发消息前先问一下"我之前跟这个 Agent 聊过吗？"

```
alice 浏览器          ChatController                    SessionAgentManager
    │                      │                                  │
    │ GET /chat/session    │                                  │
    │ ├─ agentId=agent1    │                                  │
    │ └─ sessionKey=s1     │                                  │
    │ ────────────────────>│                                  │
    │                      │                                  │
    │                      │ 1. resolveGateKey()              │
    │                      │ ├─ 构造 probe InboundMessage      │
    │                      │ ├─ chatUiChannel.previewRoute()  │
    │                      │ └─ 拿到 gateKey                   │
    │                      │                                  │
    │                      │ 2. findSessionKeyByGate()        │
    │                      │ ─────────────────────────────────>│
    │                      │                                  │
    │                      │ 3. findByGateKey(gateKey, userId)│
    │                      │ <─────────────────────────────────│
    │                      │   返回 Optional<SessionEntry>     │
    │                      │                                  │
    │                      │ 4. 存在 → exists=true             │
    │                      │    不存在 → exists=false           │
    │                      │                                  │
    │ 5. 返回               │                                  │
    │ {exists, sessionKey} │                                  │
    │ <────────────────────│                                  │
    │                      │                                  │
    │ 前端据此决定：         │                                  │
    │ - exists=true → 直接发消息（复用会话）                    │
    │ - exists=false → 也发消息（框架会自动建会话）              │
```

**关键点**：`currentSession` 只是个**查询接口**，它不创建会话。前端调它纯粹是为了"知道当前状态"，不影响后续发消息。即使它返回 `exists=false`，前端照样可以调 `stream()` 发消息——框架会在 `dispatchStream` 内部自动创建会话。

### 那 SessionAgentManager 里的会话是啥时候注册进去的？

这是个好问题，也是最容易困惑的点。经过对代码的全面追踪，真相如下：

**SessionAgentManager 中没有任何 `create()`、`register()`、`add()` 之类的方法。** 它的公开方法全是查询、重置、删除——没有"创建新会话"的能力。

追踪 `sessionsByKey.put()` 的所有调用点，只有两处：
1. `restoreFromStore()` — 启动时从 `sessions.json` 加载到内存（唯一的数据入口）
2. `resetSession()` — 重置已有会话时覆盖旧记录（不是新建）

追踪 `new SessionEntry()` 的所有调用点，也只有两处：
1. `resetSession()` 中构造重置后的 entry
2. `SessionStore.StoredEntry.toSessionEntry()` 从磁盘反序列化

**没有任何代码在运行时主动创建新的 SessionEntry 并写入内存索引！**

#### 真实的数据流：harness 直接写 sessions.json

```
┌──────────────────────────────────────────────────────────────┐
│  stream() → chatUiChannel.dispatchStream(inbound)            │
│                     │                                        │
│                     ▼                                        │
│            HarnessGateway 内部                                │
│                     │                                        │
│            ① 根据 accountId 找到或创建会话                     │
│            ② Agent 开始处理消息                                │
│            ③ 把会话元数据直接写入 workspace/sessions.json      │  ← harness 直接写文件
│            ④ 把对话日志写入 workspace/agents/{id}/sessions/    │  ← harness 直接写文件
│                                                               │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│  SessionAgentManager（本项目）                                 │
│                                                               │
│  启动时：                                                      │
│    sessionStore.load() → 从 sessions.json 读取到内存            │  ← 读 harness 写的文件
│    restoreFromStore() → 重建四个内存索引                        │
│                                                               │
│  运行时：                                                      │
│    ⚠️ 不会感知到 harness 新创建的会话！                          │
│    ⚠️ 只有 resetSession() 和 removeSession() 会修改数据        │
│                                                               │
│  下次重启时：                                                   │
│    重新 load() → 拿到 harness 在运行期间写入的所有新会话          │
└──────────────────────────────────────────────────────────────┘
```

**harness 框架和 SessionAgentManager 通过共享的 `sessions.json` 文件实现数据传递，但运行时是松耦合的——SessionAgentManager 只在启动时读一次，运行时不会感知 harness 新创建的会话。**

#### ⚠️ 潜在的同步问题

这意味着 SessionAgentManager 的内存索引在运行时可能和 `sessions.json` 不同步：

```
时间线：
  T1: 应用启动 → load() → 内存有 3 个会话
  T2: 用户 A 发消息 → harness 创建新会话 → sessions.json 有 4 个，内存还是 3 个
  T3: 用户 A 调 currentSession() → findByGateKey() → 找不到！返回 exists=false ❌
  T4: 应用重启 → load() → 内存有 4 个会话 → 现在能找到了 ✅
```

但实际上影响有限：`currentSession()` 返回 `exists=false` 时，前端只是不加载历史消息，不会阻止用户发消息——框架会在 `dispatchStream` 内部自动创建会话。用户最多是看不到之前的聊天记录，直到重启应用。

**这就是为什么你看 `stream()` 代码找不到创建会话的逻辑——它确实不创建，创建是 harness 框架干的，而且框架不是通过回调注册进 SessionAgentManager，而是直接写 `sessions.json` 文件，等下次启动时 SessionAgentManager 才能读到。**

## 三·补·续：ChatController 和 SessionAgentManager 的真实关系

基于上面的澄清，重新画一张依赖图：

```
┌─────────────────────────────────────────────────────────┐
│                    ChatController                        │
│  ┌────────────────┐  ┌─────────────────┐                │
│  │ stream()       │  │ currentSession()│                │
│  │ 发消息          │  │ 查会话是否存在   │                │
│  └───────┬────────┘  └────────┬────────┘                │
│          │                    │                         │
│          │ 不调 SAM            │ 调 SAM                   │
│          │ 只调通道            │ findByGateKey()         │
│          ▼                    ▼                         │
│  ┌──────────────┐    ┌──────────────────┐               │
│  │chatUiChannel │    │sessionAgentManager│               │
│  │.dispatchStream│   │.findByGateKey()  │               │
│  └──────┬───────┘    └──────────────────┘               │
│         │                                                │
└─────────┼────────────────────────────────────────────────┘
          │
          │ 框架内部自动创建/管理会话
          │ （直接写 sessions.json，不回调 SessionAgentManager）
          ▼
┌─────────────────────────────────────────────────────────┐
│              Harness 框架（不可见）                       │
│  ├─ ChatUiChannel.dispatchStream()                       │
│  ├─ HarnessGateway（算 gateKey、路由）                    │
│  ├─ 会话生命周期管理（创建/销毁）                          │
│  └─ 直接写 sessions.json（不回调 SessionAgentManager）   │
└─────────────────────────────────────────────────────────┘
```

**核心结论**：
- `stream()` 走的是"**通道线**"：ChatController → chatUiChannel → 框架 → Agent
- `currentSession()` 走的是"**查询线**"：ChatController → SessionAgentManager.findByGateKey()
- 这两条线**在 ChatController 内部没有交集**——stream 不查会话，currentSession 不发消息
- 它们的交集在**磁盘文件 sessions.json**：stream 触发框架创建会话并写入 sessions.json，下次启动时 SessionAgentManager 才能从 sessions.json 读到这些新会话
- **运行时**，stream 新创建的会话对 currentSession 是不可见的（内存索引不同步）

## 四、场景二：用户查看会话列表

用户 alice 打开网页，左侧栏要显示她所有的会话。这条链路跟聊天完全不同：

    │                      │                      │                    │
    │                      │ 4. 内存里过滤         │                    │
    │                      │ ├─ e.userId == alice  │（只留 alice 的）   │
    │                      │ └─ sessionMatchesAgent │（只留这个 Agent 的）│
    │                      │                      │                    │
    │                      │ 5. 给每个会话算未读   │                    │

**跟场景一的区别**：
- 场景一**写**会话（创建/更新），场景二**读**会话

- 场景一用 `gateKey` 查单个会话，场景二用 `allSessions()` 全表扫描后过滤

## 五、场景三：应用重启后恢复

这是 SessionStore 存在的**唯一理由**。进程重启后内存全没了，靠 SessionStore 恢复：

```
应用启动
    │
    ▼
SessionAgentManager 构造函数
    │
    ├─ sessionStore.load()      ← 读 sessions.json
    │   └─ 把磁盘数据加载到 SessionStore 的 entries Map
    │
    └─ restoreFromStore()       ← 重建内存索引
        ├─ 遍历 sessionStore.listAll()
        ├─ 每条记录放进 sessionsByKey（主索引）
        ├─ 有 label 的放进 labelToSessionKey
        ├─ 有 gateKey 的放进 gateKeyToSessionKey
        └─ 有 spawnedBy 的放进 childrenByParent
    │
    ▼
runMaintenance()                ← 顺手清理过期会话
    │
    ▼
SessionAgentManager 就绪，可以接客了
```

**关键点**：
- `SessionStore` 只存**会话元数据**（sessionKey、userId、agentId、文件路径等）
- 真正的**聊天记录**存在另一个地方：`agents/<agentId>/sessions/<sessionId>.log.jsonl`
- 重启后，会话元数据从 sessions.json 恢复，聊天记录从 .log.jsonl 文件读

## 六、核心概念串联：三层 Key 体系

这是整个系统最容易搞混的地方。**一个会话有三个 key**，每个 key 服务于不同场景：

### 三个 Key 是什么

| Key | 谁生成 | 格式 | 谁用 |
|---|---|---|---|
| **sessionKey** | SessionAgentManager | `UUID` | 后端内部存储的主键 |
| **conversationId** | ChatController | `UUID` 或前端传入 | 前端 URL、用户可见 |
| **gateKey** | 网关 | `\|x:agentId=agent1\|t:s1` | 网关路由用 |

### 用快递比喻

| Key | 快递比喻 |
|---|---|
| **sessionKey** | 快递单号（内部跟踪用，唯一） |
| **conversationId** | 收件地址（用户填写，对外可见） |
| **gateKey** | 分拣中心编码（分拣员用来决定送到哪个站点） |

### 三个 Key 怎么协作

```
前端（只认识 conversationId）
    │
    │ "我要看会话 s1 的历史"
    ▼
SessionController.turns(agentId, "s1", userId)
    │
    │ ① 先用 "s1" 直接查 sessionKey（老接口兼容）
    │   sessionAgentManager.getSession("s1")
    │
    │ ② 查不到？用 "s1" 当 conversationId 反查
    │   findSessionByConversationId(agentId, "s1", userId)
    │   ├─ 遍历所有会话
    │   ├─ 从每个会话的 gateKey 里提取 conversationId
    │   │   extractConversationId("|x:agentId=agent1|t:s1") → "s1"
    │   └─ 匹配上就返回
    │
    │ ③ 找到 SessionEntry，里面有 sessionKey
    ▼
用 sessionKey 去读聊天记录文件
```

### ChatController 怎么用这三个 Key

```java
// ChatController 里
String conversationId = req.sessionKey();  // 前端传来的
// ... 打包进 InboundMessage.accountId
chatUiChannel.dispatchStream(inbound);     // 网关算出 gateKey
// 网关内部：
//   gateKey = "|x:agentId=" + agentId + "|t:" + conversationId
//   sessionAgentManager.findByGateKey(gateKey)  ← 用 gateKey 查会话
```

**为什么搞这么复杂**：因为同一个用户跟同一个 Agent 可以有多个会话。光靠 `(userId, agentId)` 无法区分，必须加 `conversationId`。而 `conversationId` 是前端生成的，后端要把它编进 `gateKey` 才能做路由。

## 七、数据存在哪里（四类数据）

整个链路涉及四类数据，存在不同地方，容易搞混：

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 会话元数据（sessions.json）                                │
│    ├─ sessionKey, userId, agentId                            │
│    ├─ sessionId, sessionFilePath                             │
│    └─ gateKey, label, lastActivityMs                         │
│    谁写：harness 框架（创建会话时直接写文件）                   │
│    谁读：启动时 SessionAgentManager.restoreFromStore()        │
│    ⚠️ 运行时 SessionAgentManager 不感知 harness 新写入的数据   │
├─────────────────────────────────────────────────────────────┤
│ 2. 聊天记录（.log.jsonl）                                     │
│    └─ 每一轮对话的完整内容                                    │
│    谁写：Agent 的 memory hook（harness 框架写）               │
│    谁读：SessionController.turns() → readSessionLogContent() │
├─────────────────────────────────────────────────────────────┤
│ 3. Agent 状态（AgentStateStore：Redis 或内存）                │
│    └─ 对话上下文、记忆摘要、Plan、todo                        │
│    谁写：Agent 每轮对话结束                                   │
│    谁读：Agent 每轮对话开始                                   │
├─────────────────────────────────────────────────────────────┤
│ 4. 已读状态（readStateStore，内存）                           │
│    └─ 每个 (userId, sessionKey) 的最后已读时间                │
│    谁写：SessionController.markRead()                        │
│    谁读：SessionController.inbox() 判断未读                   │
└─────────────────────────────────────────────────────────────┘
```

**容易混淆的点**：
- **会话元数据** ≠ **聊天记录**。sessions.json 只存"有哪些会话"，不存对话内容
- **Agent 状态** ≠ **聊天记录**。Agent 状态是 Agent 的工作记忆（压缩后的摘要），聊天记录是完整的逐轮对话
- 重启后：会话元数据从 sessions.json 恢复，聊天记录从 .log.jsonl 读，但 **Agent 状态会丢**（如果用 InMemory）

## 十、常见困惑 Q&A

### Q1：为什么 ChatController 不直接调 SessionAgentManager 创建会话？
**A**：因为会话创建是**网关的职责**。网关负责"把消息路由到哪个 Agent 的哪个会话"，这个路由过程会自动创建/查找会话。ChatController 只负责"打包消息丢给网关"，不关心会话怎么管理。这样设计是**关注点分离**——ChatController 专注 HTTP 层，网关专注路由层。

### Q2：为什么 SessionStore 只存元数据，不存聊天记录？
**A**：聊天记录由 AgentScope harness 框架直接写到 `.log.jsonl` 文件，不经过本项目的代码。SessionStore 只负责"会话注册表"——有哪些会话、每个会话的文件在哪。这是**职责边界**：框架管聊天记录，本项目管会话清单。

### Q3：会话是啥时候创建的？我没看到明显的 create 逻辑
**A**：会话是**harness 框架内部自动创建**的。当 `chatUiChannel.dispatchStream(inbound)` 被调用时，框架根据 `accountId` 找到或创建会话，并**直接把会话元数据写入 `sessions.json` 文件**。这个逻辑在 AgentScope harness 框架里，不在本项目的代码里。

**关键点**：SessionAgentManager 没有任何 `create()`/`register()`/`add()` 方法。它只在启动时从 `sessions.json` 加载数据到内存。运行时 harness 新创建的会话，SessionAgentManager 不会感知到——直到下次重启时 `restoreFromStore()` 才能读到。这意味着 `currentSession()` 可能在会话刚创建后返回 `exists=false`（内存索引还没同步），但不影响功能——用户照样可以发消息。

### Q4：gateKey 那个字符串格式 `|x:agentId=...|t:...` 是谁定义的？
**A**：是 AgentScope harness 框架的 `MsgContext.canonicalKey()` 方法定义的。`|x:agentId=` 段表示路由到哪个 Agent，`|t:` 段表示哪个会话线程。本项目只是**解析**这个字符串（见 `extractGatewayAgentId` / `extractConversationId`），不生成它。

### Q5：为什么 inbox 要全表扫描？不能按 userId 查吗？
**A**：当前实现确实全表扫描，因为 `SessionAgentManager` 没有按 userId 的索引。这是个**性能隐患**，但在中小规模场景下可以接受。如果要优化，应该在 SessionAgentManager 加一个 `userIdToSessionKeys` 索引。

### Q6：会话重置（reset）和删除（delete）有啥区别？
**A**：
- **reset**：会话还在，只是清空 Agent 的记忆（分配新的 sessionId，旧的聊天记录文件不动）。像"换个新本子"。
- **delete**：会话彻底没了，从内存和磁盘都删除。像"把整个档案销毁"。

## 十一、总结：一句话理解协作关系

> **ChatController 是"聊天入口"，SessionController 是"管理入口"，两者都把脏活累活丢给 SessionAgentManager（会话中枢），SessionAgentManager 再把持久化丢给 SessionStore（磁盘小弟）。harness 框架在背后直接写 sessions.json 创建会话，SessionAgentManager 只在启动时从 sessions.json 加载数据——运行时两者是松耦合的。**

四个文件，一个比一个底层：
- ChatController / SessionController → **HTTP 层**（接请求）
- SessionAgentManager → **业务层**（管会话——查询、重置、删除、清理，但不创建）
- SessionStore → **持久层**（存磁盘）

harness 框架 → **会话生产者**（创建会话、写 sessions.json、写聊天日志）

理解了这个层次关系，再回去看代码就清晰了。

## 附录：Session* 文件完整清单与职责

本项目中有 10 个 Session 相关文件，它们构建的是一个"聊天管理后台"，而不是"打电话的能力"。

### 第一层：数据模型（纯数据结构）

| 文件 | 类型 | 职责 |
|------|------|------|
| `SessionEntry.java` | Record | 一条会话档案（谁、跟谁聊、什么时候、日志在哪） |
| `SessionKind.java` | Enum | 会话类型：主会话（MAIN）vs 子代理会话（SUBAGENT） |
| `HistoryResult.java` | Record | 读取历史的结果包装 |

### 第二层：存储引擎（数据的读写）

| 文件 | 职责 | 类比 |
|------|------|------|
| `SessionStore.java` | 把会话元数据持久化到 `sessions.json` | 硬盘上的档案柜 |

关键细节：
- 启动时 `load()` → 从磁盘加载到内存
- 运行时 `save()` → 内存变更同步到磁盘
- 用**临时文件+原子重命名**保证写入安全
- **harness 框架也会直接写 `sessions.json`**（创建新会话时），SessionStore 只在 reset/remove 时写

### 第三层：核心管理器（业务逻辑）

| 文件 | 职责 | 提供的能力 |
|------|------|-----------|
| `SessionAgentManager.java` | 会话的 CRUD + 维护 | 查询、重置、删除、过期清理、总数限制 |

四个内存索引：
```
sessionsByKey         // 按 sessionKey 查（主索引）
labelToSessionKey     // 按标签名查
gateKeyToSessionKey   // 按网关路由键查（ChatController 用这个）
childrenByParent      // 查子代理会话
```

⚠️ **没有 `create()`/`register()`/`add()` 方法**——数据唯一入口是启动时从 `sessions.json` 加载。

### 第四层：配置（控制行为）

| 文件 | 职责 |
|------|------|
| `AgentManagerConfig.java` | 维护策略配置 |
| `SessionMaintenanceConfig.java` | 过期清理规则（多久清、最多留多少） |

### 第五层：Web 层（对外暴露 API）

| 文件 | 职责 | 对应的前端页面 |
|------|------|---------------|
| `SessionController.java` | REST API：收件箱、查看详情、重置、删除、标记已读 | 微信的"聊天列表"+"聊天详情"页 |

提供的接口：
```
GET    /api/agents/{id}/sessions/inbox      → 收件箱列表
GET    /api/agents/{id}/sessions/{key}       → 对话详情
POST   /api/agents/{id}/sessions/{key}/reset → 重置会话
PATCH  /api/agents/{id}/sessions/{key}/read  → 标记已读
DELETE /api/agents/{id}/sessions/{key}        → 删除会话
```

### 第六层：辅助工具（支撑功能）

| 文件 | 职责 | 类比 |
|------|------|------|
| `SessionTurnParser.java` | 把原始 JSONL 日志翻译成结构化对话轮次 | 会议记录整理员 |
| `SessionReadStateStore.java` | 跟踪每个会话的已读/未读状态 | 微信的红点提醒系统 |
| `SessionLifecycleScheduler.java` | 定时任务：空闲重置、每日重置、定期清理 | 定时清理工 |

### 用微信类比理解

| 组件 | 对应微信的功能 | 在项目中 |
|------|--------------|---------|
| `ChatController` (stream/send) | 发消息/接电话 | **聊天能力**（harness 提供） |
| `SessionController` | 聊天列表 + 聊天记录 + 删除聊天 | **会话管理 UI** |
| `SessionAgentManager` | 后台的聊天记录数据库 | **会话数据层** |
| `SessionStore` | 聊天记录存到手机本地 | **持久化层** |
| `SessionTurnParser` | 把聊天记录格式化展示 | **日志解析器** |
| `SessionReadStateStore` | 未读红点提醒 | **已读状态跟踪** |
| `SessionLifecycleScheduler` | 自动清理过期聊天 | **定时任务** |

**如果你只关心"怎么发消息、怎么收到回复"，那确实不需要任何 Session* 文件。但如果你想做一个完整的聊天产品（有历史记录、有聊天列表、能删除、能重置），那就必须要有这套基础设施。**
