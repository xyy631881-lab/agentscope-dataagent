## (1) 统一 Agent 运行时与多子 Agent 协作

**原文：** 统一全局与用户Agent，集成上下文压缩、长期记忆和模型容错，并通过探索/报告子Agent完成任务协作。

**优化后（简历正文）：**

> 设计 `AgentRuntimeConfigurer` 作为全局 Agent（bootstrap 注册）与用户自定义 Agent 的统一运行时装配器，收敛状态存储、沙箱、Trace 中间件、权限、子 Agent 等 7 类能力配置，消除双路径配置漂移。集成上下文压缩（消息阈值 30 触发 / 保留 10 条 + 工具结果淘汰）、长期记忆（10 分钟节流刷新）与模型容错（2 次重试 + fallback 模型链）；预设 `data-explorer`（隔离工作区、不暴露用户）与 `report-writer`（共享工作区、产出 Markdown 报告）两个角色化子 Agent，通过工作区隔离 / 共享模式实现"探查—报告"分工协作。

**代码实证：**
- `AgentRuntimeConfigurer` 类注释明确："Both DataAgentBootstrap (for global agents) and AgentLifecycleService (for user-custom agents) apply this configurer" —— 统一装配器
- `b.compaction(CompactionConfig.builder().triggerMessages(30).keepMessages(10).build())` + `b.toolResultEviction(ToolResultEvictionConfig.defaults())` —— 压缩 + 工具结果淘汰
- `b.memory(MemoryConfig.builder().flushTrigger(MemoryConfig.FlushTrigger.throttled(Duration.ofMinutes(10))).build())` —— 节流长期记忆
- `b.maxRetries(2)` + `b.fallbackModel(fallbackModelId)` —— 重试 + fallback
- `defaultSubagentDeclarations()`：`data-explorer`(WorkspaceMode.ISOLATED, maxIters 30, exposeToUser false) + `report-writer`(WorkspaceMode.SHARED, maxIters 25, exposeToUser true) —— 工作区模式差异是设计亮点（explorer 隔离探查、writer 共享发布到主工作区供父 Agent 与 UI 读取）

**面试追问清单：**
1. 统一装配器收敛了哪 7 类能力？为什么不能让全局 Agent 和用户 Agent 各自配置？（双路径配置漂移风险）
2. 上下文压缩的"30 触发 / 10 保留"是怎么实现的——滑动窗口截断还是摘要压缩？压缩后历史信息丢失怎么补救？（追问框架 Compaction 机制：是截断还是 LLM 摘要？）
3. 工具结果淘汰（ToolResultEviction）和消息压缩是什么关系？为什么要单独淘汰工具结果？（工具结果体积大、可重算）
4. 长期记忆 10 分钟节流刷新——为什么用节流而不是每轮写？记忆存哪？怎么检索？（向量检索 / KV / 全量？）
5. fallback 模型链触发条件是什么？主模型超时、限流、内容审核失败分别走哪条？fallback 后会回切主模型吗？
6. data-explorer 用 ISOLATED、report-writer 用 SHARED——为什么不都用 SHARED？explorer 的隔离工作区探查结果怎么传给 writer？（追问工作区模式设计意图）
7. 子 Agent 是并行还是串行调用？maxIters 30/25 怎么定的？子 Agent 失败会不会拖垮主 Agent？

## (2) 数据分析工具链与 HITL 安全闭环

**原文：** 实现元数据探查、SQL预览和图表工具，结合只读校验、HITL审批，支持查询确认、主动取消和进度反馈。

**优化后（简历正文）：**

> 基于 Spring JdbcTemplate 实现 4 个数据分析原语工具：`list_data_sources`（数据源发现）、`describe_table`（DatabaseMetaData 元数据探查 + 采样）、`run_sql_preview`（只读 SQL 预览，Markdown 表格输出）、`render_chart`（Vega-Lite 图表）。SQL 工具采用三层只读校验——白名单（仅 SELECT/WITH）+ 黑名单（9 种 DDL/DML 关键词）+ `setMaxRows(500)` 行数硬上限（用 JDBC API 而非拼接 LIMIT，规避方言差异），辅以标识符清洗防表名注入。落地完整 HITL 闭环：`PermissionMode.BYPASS` + 单条 ASK 规则拦截 `run_sql_preview`，经 `RequireUserConfirmEvent` 下发 confirm 帧 → 用户审批 → `ConfirmResult` 回传恢复暂停的 Agent；配合 SSE 流式推送 6 类执行帧（token / tool_call / tool_result / confirm / done / error）实现实时进度反馈，`/cancel` 端点 + 180s idle timeout 支持主动取消。

**代码实证：**
- `DataAgentToolkit`：4 个 @Tool 方法；`runSqlPreview` 三层校验（lower.startsWith select/with → 9 关键词黑名单 insert/update/delete/drop/alter/create/truncate/merge/replace → `Math.min(rowLimit, 500)`）
- `setMaxRows(rowLimit)` 用 `ConnectionCallback` 在建 Statement 后立刻调用——"无论什么数据库方言都生效"（代码注释原话）
- `sanitizeIdentifier(name)`：`replaceAll("[^a-zA-Z0-9_]", "")` 防表名注入
- HITL：`AgentRuntimeConfigurer.buildPermissionContext()` = `PermissionMode.BYPASS` + `addAskRule("run_sql_preview", ...)`；注释明确"BYPASS does NOT mean allow everything——fallback 是 ALLOW，但 ASK 规则先于 BYPASS 求值"，刻意不用 DEFAULT 模式（fallback 是 ASK，会逼出长 allow-list，单个 key 写错就静默退回 ASK 卡死）
- `ChatController`：`RequireUserConfirmEvent` → `pendingConfirms.put` + confirm SSE 帧 → `ConfirmDecision` 回传 → `buildConfirmResults` 匹配 toolCallId 恢复
- 取消：`@PostMapping("/cancel")` + `activeStreams.remove` + `subscription.dispose()` + 权限校验（`!userId.equals(active.userId())` 抛 403，不能取消别人的请求）+ `.timeout(Duration.ofSeconds(180))` 防 idle stream 永久挂起
- 进度反馈：`convertToSseFrame` 6 类事件→6 类 SSE 帧

**面试追问清单：**
1. 三层只读校验为什么不够、还要加标识符清洗？黑名单能不能被绕过（如大小写、注释、嵌套子查询藏 DROP）？（追问 SQL 注入边界）
2. 为什么用 `setMaxRows` 而不是拼 `LIMIT`？Oracle 不支持 LIMIT，但你的黑名单是基于关键词包含判断，`LIMIT` 本身不会被拦——这里有没有矛盾？（追问方言兼容与校验顺序）
3. BYPASS + 单 ASK 规则的设计——为什么不用 DEFAULT 模式枚举 allow-list？"单个 key 写错静默退回 ASK 卡死"具体是什么 bug？怎么发现的？
4. HITL confirm-back channel：Agent 被暂停后状态保存在哪？用户审批后怎么"恢复"而不是"重新开始"？`pendingConfirms` 是内存 Map，多副本下会不会丢？（追问分布式 HITL）
5. `ConfirmDecision` 的 toolCallId 怎么和原始 ToolUseBlock 匹配？如果用户拒绝，Agent 收到什么？继续走 fallback 还是终止？
6. 6 类 SSE 帧里 `tool_call` 和 `tool_result` 为什么分开发？前端怎么把它们配对？（toolCallId 关联）
7. 主动取消时，Agent 已经发出的模型调用怎么处理？`subscription.dispose()` 能中断 Reactor 流吗？已经执行的副作用（如已写文件）回滚吗？
8. 180s idle timeout——"idle"是怎么判定的？如果模型在长思考（>180s）会不会被误杀？

## (3) Agent 热重建与租户级多模型路由

**原文：** 实现Agent热重建与多模型路由，使提示词、模型和工具配置实时生效，并按用户动态解析模型连接。

**优化后（简历正文）：**

> 实现 Agent 热重建机制：`DataAgentBootstrap` 将全局 Agent 集合改造为 `ConcurrentHashMap`，配置变更后从合并层（bootstrap 定义 ⊕ 全局覆盖层）重建 Agent、重绑实例化工具、原子交换 `HarnessGateway` 与本地映射并关闭旧实例，提示词 / 模型 / 工具配置秒级生效且零重启，在线会话按 agentId+conversationId 维度无感续接。落地租户级多模型路由 `TenantModelService`：`resolve(userId, modelId)` 优先按租户配置（解密 apiKey + baseUrl + endpoint + stream + cachePolicy）经 `ModelCreationContext` 构建连接，缺失则降级到 `ModelRegistry` 静态注册；支持 OLLAMA / OPENAI_COMPATIBLE 双 provider，apiKey 用 AES 加密落库，按租户三档 token 单价（标准输入 / 缓存输入 / 输出）计算微美元级成本。

**代码实证：**
- 热重建：`DataAgentBootstrap.rebuildGlobalAgent(id)`（记忆确认）—— `agents` 为 `ConcurrentHashMap`，`registerMainAgentToolInstaller` Hook 让 `DataToolkitRegistrar`/`ContributionToolRegistrar` 在重建期重绑实例化工具；原子交换 `HarnessGateway` + local map，close 旧 Agent；`AgentMutationService.updateGlobalAgent` 保存后触发
- 租户路由：`TenantModelService.resolve(userId, logicalModelId)` → `repository.findByTenantIdAndLogicalModelId(tenantForUser(userId), ...)` → `resolveConfigured`：`ModelCreationContext.builder().apiKey(cipher.decrypt(...)).baseUrl(...).stream(TRUE).cachePolicy(ENABLED).cacheId(tenantId+logicalModelId+updatedAtMs).option("modelName", ...).build()` → `ModelRegistry.resolve(factoryId, context)`（factoryId = `tenant-ollama` / `tenant-openai`）；无租户配置则 `ModelRegistry.resolve(normalizeLogicalId)` 降级
- `tenantForUser(userId) = userId`（当前用户即租户，注释明确"未来组织表可替换此映射无需模型迁移"）
- 成本：`calculateCostMicrousd(userId, logicalModelId, inputTokens, outputTokens, cachedPromptTokens)` —— `perMillion(标准输入, inputMicrousdPerMillion) + perMillion(缓存输入, cachedInputMicrousdPerMillion) + perMillion(输出, outputMicrousdPerMillion)`，微美元精度
- AES：`TenantModelCredentialCipher.encrypt/decrypt`，apiKey 字段 `apiKeyCiphertext`；OpenAI 兼容 provider 强制要求 apiKey

**面试追问清单：**
1. 热重建的"原子交换"具体交换什么？`HarnessGateway` 和 local map 是两个引用，如何保证一致？有没有双写不一致窗口？
2. 重建后在线会话"无感续接"——旧 Agent 被 close 后，旧会话的下一步请求怎么路由到新实例？记忆 / 上下文怎么续上？（agentId+conversationId 维度存活，但 Agent 实例变了，系统提示词也变了，怎么处理上下文断裂？）
3. 实例化工具 vs 静态工具——为什么要重新绑定？工具闭包持有的旧 Agent 实例引用会不会内存泄漏？GC 能回收吗？
4. 并发场景：两个管理员同时改同一全局 Agent 怎么办？有没有乐观锁？重建过程中来了新请求怎么路由（旧还是新）？
5. 租户模型 `resolve` 优先租户配置、缺失降级 `ModelRegistry`——降级时缓存策略、stream 配置都丢了，会不会行为不一致？为什么不让静态注册也走 ModelCreationContext？
6. `cacheId = tenantId + logicalModelId + updatedAtMs`——这个 cacheId 是 prompt cache 的 key 吗？租户改配置后 updatedAtMs 变了，缓存自动失效？跨租户会不会缓存串扰？
7. apiKey 用 AES 加密落库——加密 key 怎么管理？轮换怎么办？多副本下各节点能用同一份密文吗？
8. 三档 token 单价（标准输入 / 缓存输入 / 输出）——为什么要区分缓存输入？这对应 prompt caching，你的框架真的支持吗？cachedPromptTokens 从哪取？

## (4) OpenTelemetry 请求级 Trace 与成本可观测

**原文：** 接入OpenTelemetry构建请求级Trace，异步聚合Token、耗时、状态与成本，支持异常定位和模型开销分析。

**代码实证：**
- root span：`GlobalOpenTelemetry.getTracer("io.agentscope.dataagent.chat").spanBuilder("dataagent.chat.run").setSpanKind(SpanKind.SERVER).setAttribute(agent.id/session.key/request.model).startSpan()`
- 中间件：`AgentRuntimeConfigurer` → `b.middleware(new OtelTracingMiddleware())`，注释"Emits child spans for agent, model and tool execution"
- 上下文传播：`ContextPropagationOperator.runWithContext(events, traceScope.otelContext())` —— Reactor 流里 trace 不丢
- 桥接：`TraceRunService.start`（建 TraceRunEntity，含 tenantForUser 租户隔离）→ `appendSpan`（`EXPORTED_ATTRIBUTES` 白名单 11 个 key 过滤 + `durationMs = (endNanos - startNanos)/1_000_000`）→ `complete`（`run.finish(outcome, conciseError, now)`，error 截断 1000 字符）
- 聚合：`UsageTotals`（3 个 AtomicLong）在 `ModelCallEndEvent` 时 `add(usage)`；`doFinally` 里 `usageStore.record(UsageEvent{tenantId, userId, agentId, conversationId, modelId, inputTokens, outputTokens, cachedPromptTokens, durationMs, costMicrousd, outcome, timestamp})`
- 成本：`tenantModels.calculateCostMicrousd(userId, logicalModelId, inputTokens, outputTokens, cachedPromptTokens)` —— 与第 3 条 TenantModelService 联动
- 异常定位：`conciseError`（`replaceAll("\\s+"," ").trim()` + 截断 1000）+ `error.type` attribute + `TraceRunEntity.errorMessage` + outcome；`recentForUser` 分页查最近 100 条 run
- 状态：`outcomeFor(signalType)` —— ON_COMPLETE→SUCCESS / CANCEL→CANCELLED / else→ERROR

**面试追问清单：**
1. root span 是 SERVER 级，子 span 由 `OtelTracingMiddleware` 发——这个中间件是框架提供的还是你写的？span 之间的 parent 关系怎么建立的？（parentSpanId 传播）
2. `ContextPropagationOperator.runWithContext` 解决了什么问题？Reactor 流跨线程时 trace 上下文为什么会丢？不用它会怎样？
3. 11 个 EXPORTED_ATTRIBUTES 是白名单过滤——为什么不全量导出？attributes 可能含敏感信息（用户输入）？白名单怎么定的？
4. `appendSpan` 是异步导出，如果 DB 写入慢会不会阻塞 agent 流？有没有批量 / 背压？`spans.existsBySpanId` 去重每次都查库，高并发下性能怎样？
5. UsageTotals 用 3 个 AtomicLong——为什么不用同步块或 LongAdder？`ModelCallEndEvent` 在多线程并发触发时累加准确吗？
6. 成本计算放在 `doFinally`——如果流被 cancel（用户主动取消），`doFinally` 还会执行吗？此时 token 已经部分累加，成本怎么算？（追问 Reactor doFinally 语义）
7. "按模型聚合做开销分析"——`UsageStore` 的表结构是什么？按 modelId 聚合的查询走索引吗？支持按时间范围 / agent / 用户维度下钻吗？
8. `conciseError` 截断 1000 字符——为什么是 1000？太短的错误信息会不会丢失堆栈？error.type attribute 和 errorMessage 是什么关系？
9. traceId 是 64 位——跨服务调用时能不能传出去？有没有对接 Jaeger / Tempo 等后端？还是只存了自己的 DB？
