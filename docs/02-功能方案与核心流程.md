# 功能方案与核心流程

本章按“用户能看到什么、后台如何实现、数据在哪里、边界是什么”描述功能。接口名称用于定位代码，不承诺稳定的外部 OpenAPI 合约。

## 1. 认证、用户与管理员

**用户目标**：登录后进入工作台；管理员还能进入治理后台。

**方案**：`AuthController` 登录并签发 JWT；`SecurityConfig/JwtService` 解析身份和角色；`UserController` 管理当前用户资料与改密；`AdminUserController` 管理用户及角色。

**权限边界**：

- 普通用户只能访问自己的个人资源。
- 管理员的前端路由由 `AdminRoute` 引导，但后端 `/api/admin/*` 才是强制校验点。
- 密码、JWT、模型 API Key 都不得写入前端日志、Trace attributes 或普通查询响应。

## 2. Agent 目录、创建与热重建

**用户目标**：使用团队 Agent，或创建自己的 Agent，配置模型、提示词、工具、技能和沙箱策略。

**关键类**：`AgentCatalogController`、`AgentMutationService`、`AgentLifecycleService`、`AgentAclService`、`WorkspaceResolutionService`。

**创建私有 Agent 的流程**：

```text
创建请求
  -> 校验 ID、配置和 owner
  -> UserAgentDefinitionStore 保存定义
  -> 在 users/{userId}/agents/{agentId} 生成/实例化工作区
  -> 首次复制团队基础数据 Skill 并写迁移标记
  -> 下一次访问或聊天时 AgentLifecycleService 懒构建 HarnessAgent
  -> Gateway 注册 user:{userId}:{agentId} 风格的运行实例
```

**热重建策略**：配置更新后使对应 UCA（user custom agent）缓存失效，新请求按最新定义构建；在途请求不应被强制终止。模型优先从用户级 `TenantModelService` 解析，未配置时回退全局静态模型。

**基础 Skill 迁移规则**：新私有 Agent 可以获得团队的基础数据 Skill；历史私有 Agent 首次升级时若已有任意 Skill 目录，系统只写迁移标记，不会把用户已卸载的 `chart-rendering` 又复制回来。

## 3. 聊天、SSE、工具轨迹与人工确认

**用户目标**：看到模型流式回复、工具执行轨迹，并对敏感操作做批准或拒绝。

**关键类**：`ChatController`、`ConversationService`、前端 `ChatPage`、`ChatPanel`、`ToolCallBlock`。

**流程**：

```text
POST/流式聊天请求
  -> 校验 userId、agentId、sessionKey
  -> 建立 AgentScope 输入消息和 Trace 根 span
  -> 订阅 Agent 事件流
  -> 映射 token / tool call / tool result / approval / done / error 为 SSE
  -> 浏览器增量渲染回复与“执行轨迹”
  -> finally: 关闭 Trace、写 Usage、更新会话和工作区演化
```

**HITL**：`run_sql_preview` 等需要确认的工具先产生待确认事件；用户拒绝时不执行，批准后通过原始 tool call 上下文继续。UI 使用站内 `InteractionHost` 的 Promise 确认框和通知，不调用浏览器原生 `confirm()`/`alert()`。

**停止与异常**：用户取消、模型异常、工具异常都要结束 SSE、清理 pending confirm，并把结果标为 `CANCELLED` 或 `ERROR`。观测写入不能反向阻塞主回复。

## 4. 数据分析工具与图表

**用户目标**：让 Agent 发现数据源、查看表结构、在人工批准后执行只读 SQL，并生成图表。

**工具**：

- `list_data_sources`：返回已注册的数据源。
- `describe_table`：查看字段和样例。
- `run_sql_preview`：执行受控只读查询。
- `render_chart`：服务端校验规格，前端用 Vega Embed 渲染。

**安全策略**：这是多层防御，不是单一关键词过滤：应用层语句校验、行数限制、查询超时、HITL，以及生产环境应使用数据库只读账号。Vega 规格只接受受控类型和内联数据，不能允许任意远程 URL。

**边界**：SQL 解析和权限策略还需要持续扩展；不能因为“页面有批准按钮”就宣称任意 SQL 已绝对安全。

## 5. 会话、工作区与 Sandbox

**用户目标**：每个 Agent 会话可恢复，生成的 `reports/`、图表和计划可以在工作区中查看。

**关键类**：`SessionController`、`ConversationService`、`WorkspaceFileService`、`WorkspaceSummaryService`、`WorkspaceManagerFactory`、`RetryStartDockerSandbox`。

**规则**：

- 会话元数据和索引进入 MySQL；Agent 上下文/运行态由 AgentScope state store 管理。
- 工作区写操作走 Sandbox 文件系统；`local-workspaces/{userId}/{agentId}` 是只读镜像，可用于快速浏览和故障降级。
- 文件名和路径必须归一化并限制在工作区内，阻止 `../` 和绝对路径逃逸。
- Docker Sandbox 使用用户隔离命名空间，并可在 Redis profile 下持久化 snapshot、用 execution guard 串行化同一隔离槽。

**为什么不直接用本地镜像写文件**：镜像不是运行时事实来源。直接写镜像会绕过容器、状态和框架生命周期，造成页面显示与 Agent 实际看到的文件不一致。

## 6. 子 Agent、技能与偏好学习

**用户目标**：主 Agent 能将专项任务委派给子 Agent；用户可安装/编辑技能，Agent 会基于其成功使用习惯逐步调整提示词。

**子 Agent**：`AgentRuntimeConfigurer` 给运行实例装配统一的 Plan、Memory、Permissions、Sandbox 和子 Agent 声明。子任务以独立上下文和工作区策略运行，结果再返回主 Agent；管理员会话页可查看主/子会话树。

**技能**：私有工作区的 `skills/` 是最内层覆盖；可叠加用户定义的外部 Skill repository。安装市场版本时采用 staging 目录完整物化，再替换目标目录，写入安装元数据并失效 Agent/Sandbox 状态，使后续请求加载新文件。

**偏好学习**：`PreferenceRecorder` 记录成功的 SQL/图表行为；`UserPreferenceService` 将聚合偏好形成提示词片段；`AgentLifecycleService` 构建私有 Agent 时追加这段片段。偏好按 `userId + agentId` 隔离，不能写回全局 Agent 配置。

## 7. 贡献、审批和 Marketplace

**用户目标**：将私有 Skill/子 Agent/图表模板等能力提交给团队，经审核后可版本化安装和回滚。

**关键类**：`MarketContributionController`、`ContributionApprovalController`、`MarketContributionService`、`SkillInstallService`、`LocalApprovalMarketplace`。

**状态机**：

```text
私有工作区文件
  -> PENDING（提交原稿）
  -> APPROVED（审核稿发布并归档版本）
  -> Marketplace 可选版本安装
  -> 可回滚到归档版本

PENDING -> REJECTED
```

**治理规则**：提交人与审核人分离；版本应不可变；发布时记录来源、审核人、版本和审核内容。批准、文件发布、Redis 状态失效跨越多个资源，当前实现追求可观测与可重试，并不是分布式强事务。

## 8. 用户级模型连接

**用户目标**：每个用户可以配置自己的模型提供商、Base URL、模型名、密钥与成本单价，私有 Agent 使用该连接。

**关键类**：`TenantModelController`、`TenantModelService`、`TenantModelCredentialCipher`、前端 `TenantModelsPage`。

**设计**：用户 ID 当前作为过渡 tenant ID。API Key 用 AES-GCM 加密，接口只接受写入、不回显明文；构建 Agent 时通过 `ModelCreationContext` 解析。未配置用户连接或解析失败时，使用 bootstrap 的 local/longcat 注册模型作为 fallback。

## 9. 用量与运行记录

### 9.1 用量账本

每次完成聊天请求，`ChatController` 聚合该回合的全部模型调用使用量，写入一条 `UsageEvent`：输入 Token、输出 Token、缓存 Prompt Token、模型、耗时、微美元成本、结果状态和时间。

`UsageStore` 提供个人和平台两种聚合：摘要、小时趋势、每日趋势、模型分布，以及管理员专属的用户/Agent 排行。

前端 `/usage` 是唯一用量入口：

- 普通用户：只请求 `/api/usage/me/*`，只看到自己的数据。
- 管理员：默认请求 `/api/admin/usage/*` 看平台数据，也可切换到个人数据。
- 旧 `/admin/usage` 仅做跳转，避免两个页面长期漂移。

### 9.2 OTel Trace

AgentScope 的 `OtelTracingMiddleware` 生成 Agent、模型和工具 span；`TraceRunService` 将其持久化为可查询索引。只保留模型、Token、工具名、调用数、reply id、错误类型等白名单属性，不把 Prompt、模型全文或密钥写入 span 索引。

用户在 `/traces` 查看自己的运行记录；管理员相关页面用于查看更广的会话与运行状态。

## 10. 通道、Webhook 与绑定偏好

**通道**表示外部消息入口与 Agent 路由，而不是单条聊天消息。浏览器 ChatUI 走默认通道；外部 IM/Webhook 需要相应适配器和绑定规则。

平台提供通道目录、身份关联和用户频道偏好能力。前端收到的 API 响应必须始终验证 `Content-Type` 与 HTTP 状态；若把 HTML 回退页当 JSON 解析，页面会出现 `Unexpected token '<'`，应优先检查请求路径、反向代理和静态资源版本是否匹配。

## 11. 前端壳与交互规则

- `AppShell` 承载聊天侧栏和所有用户工具页；其主内容层可纵向滚动，防止固定视口裁掉长表单、表格和用量页。
- 页面内部已经有专属滚动需求时（聊天消息区、工作区编辑器、技能市场 modal、运行记录），保留独立滚动，避免整页与局部滚动混乱。
- 管理台使用独立 `AdminAppShell`，不要嵌在聊天壳里；重复的“用量”入口已迁出管理侧栏。
- 破坏性操作统一走站内确认框，错误用通知呈现；不要新增浏览器原生弹窗。
